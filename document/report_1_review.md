## 1. 手法の妥当性について

### ✅ 良い点

*   **PIMC法（Perfect Information Monte Carlo）** は、不完全情報ゲームのAI開発における標準的なアプローチであり、学術的にも広く認められた手法です。
*   「キャラクターパラメータをプレイアウトポリシーに適用する」というアイデアは、AIの強さと個性を両立させる上で有効です。

### ⚠️ 懸念点・補足すべき点

*   **「終盤完全読み（Endgame Solver）」の計算量**: フェーズ1で提案されている「手札15枚以下でMinimax法に切り替える」は、計算量の見積もりが甘い可能性があります。
    *   大富豪は4人対戦であり、探索の分岐数（各プレイヤーの候補手の数）が非常に多くなります。
    *   仮に各局面で平均5通りの合法手があるとすると、4人×5手先で $5^{20}$ = 約95兆通りの探索が必要になり、現実的ではありません。
    *   **対策案**: Minimax法ではなく、深さを制限したモンテカルロシミュレーション（ランダムプレイアウト）や、Iterative Deepeningを併用すべきです。

---

## 2. スマホ環境への適合性について（発熱・計算能力）

> [!CAUTION]
> 本プロジェクトはユーザの70%がスマートフォンからのアクセスです。**report_1.md で提案されている手法は、デスクトップPCを前提としており、スマートフォンへの配慮が欠けています。**

### ❌ 深刻な懸念点

| 項目 | デスクトップ | スマートフォン |
|---|---|---|
| CPU | 十分なマルチコア性能 | シングルスレッド性能が低い。サーマルスロットリングにより持続的な高負荷処理でクロックダウン |
| 処理時間の許容度 | 3〜5秒の「思考時間」はストレスになりにくい | 毎ターン3〜5秒待たされるとユーザ体験が著しく悪化する |
| 発熱 | ファンで冷却可能 | **ファンレスのため発熱がダイレクトにUXに影響**（端末が熱くなる） |
| バッテリー | 常に給電 | **バッテリー消耗が激しいとユーザ離脱の原因に** |
| JavaScript実行環境 | V8 (Chrome) の最適化が効きやすい | モバイルブラウザはデスクトップより2〜5倍遅いことがある |

### 📊 現実的な試算

*   PIMC法でサンプリング100回、各サンプリングで50手のプレイアウトを行う場合、1ターンあたり **5000回** のゲームシミュレーションが必要になります。
*   JavaScriptで1回のシミュレーションに1ms かかると仮定すると、1ターンあたり **5秒** かかります。
*   スマートフォンではこれが **10〜25秒** になる可能性があり、発熱とバッテリー消耗も深刻になります。

## 3. 改善提案

report_1.md の手法を実用化するためには、以下の修正・追加が必要です。

### 提案A: 思考時間の「時間制限」を設ける

MCTSの「エニータイム」特性を活かし、シミュレーション回数ではなく**許容時間（例: 500ms）**を上限とします。
*   500msで終わるだけのシミュレーションしか行わない。
*   スマホでは回数が減るが、待ち時間は固定される。

### 提案B: Web Workerの活用

メインスレッドをUIに使い、**探索処理は Web Worker で別スレッド化**することで、UI のカクつきを防ぎます。
*   ただし、Web Workerはスマートフォンでは効果が限定的な場合があります（コア数が少ないため）。

### 提案C: 「思考レベル」の導入

ユーザが難易度（思考レベル）を選択できるようにし、スマホユーザには軽量モードを推奨します。
```
レベル1: 現行のヒューリスティック（貪欲法）- 軽量
レベル2: 終盤のみ簡易探索（深さ2のMinimax）- 中量
レベル3: フルPIMC（PCユーザ向け）- 重量
```

### 提案D: 段階的なアプローチ

report_1.md の「フェーズ1: 終盤完全読み」をさらに分割し、まずは**「あがり確定判定」**だけを実装します。
*   「この手を出せば100%上がれる」場合にのみ特別なロジックを発動。
*   計算量は極めて軽く、スマホでも問題なく動作します。

| 観点 | 結論 |

| スマホ環境への適合 | ❌ 現状の提案ではスマホで実用的ではない。**時間制限付きMCTS**や**思考レベル選択**などの追加施策が必須。 |
